Use cases / Changelogs

Keep a clear record of every product change

A changelog is a list of important changes in each release. It tells people what changed and why it matters. Open Knowledge keeps this list close to the work.

Release notes should not require detective work

Details often live in code, tests, reviews, and conversations. At release time, someone must find the changes that matter to users.

  • The code note says too little.“Update parser” does not explain what a user will see.
  • The release owner starts again.The reason and user impact may be hard to find later.
  • Guides and history become mixed.A guide explains the product now. A changelog explains what changed.

Record a product change while its code, tests, and reason are still together.

First, set up Open Knowledge

Store the changelog as a simple Markdown file in the project. Open Knowledge can tell an AI agent when it should suggest an entry.

  1. Install Open Knowledge

    If okn version already works, skip this command.

    $ curl -fsSL https://openknowledge.sh/install | bash

  2. Create the knowledge base

    Start the guided setup in the project that owns the product.

    $ okn setup Wiki --interactive

  3. Add the changelog rule

    Add the built-in rule to the project instructions.

    $ okn prompt rules apply changelog --path Wiki --file AGENTS.md

The rule covers changes that users can see. It also covers setup, publishing, and package changes. It skips internal cleanup that users cannot see.

Start with current guides and one changelog

A small knowledge base needs one place for current instructions. It also needs one place for the history of important changes.

Current guides
How the product works now, with instructions and examples.
Changelog
What users gained or what they need to change for each release.
log.md
An optional file for changes to the knowledge base itself. It does not record product changes.
Wiki/
├── index.md
├── features/
│   └── citation-review.md  # current behavior
├── changelog/
│   └── editor-helper.md    # release history
└── log.md                 # knowledge-base update history

Open Knowledge uses this structure today. The guides explain the current product. The changelog explains what changed in each release.

Ask the AI agent whether users will notice the change

The rule gives the AI agent one clear decision. If users will notice the change, the agent suggests a short entry. Otherwise, it leaves the changelog unchanged. 

Before finishing a code change:
1. Decide if users will notice the change.
2. If they will, update the current guide.
3. Suggest a short changelog entry.
4. Add links to the code and guide.
5. Skip the entry for formatting-only or internal cleanup.

Open Knowledge provides the rule and files. The AI agent suggests the text. A person still checks and approves the claim.

Review the entry before you publish it

A reviewer can check the code, tests, current guide, and changelog together. The entry must describe the real result for users.

Before approval, check three things:

  • Does the entry describe a user-visible outcome?
  • Do the file and guide links support the claim?
  • Does Open Knowledge report a valid knowledge base?
$ okn validate Wiki

Validation checks file structure, document details, Markdown, and local links. A person must still check the meaning of the entry.

Release notes become easier to prepare

The changelog grows through small reviewed entries. At release time, the team edits known entries instead of searching for forgotten changes.

  • Less searchingThe team records user impact while the details are still clear.
  • Fewer repeated questionsRelease owners start with reviewed entries from each change.
  • One clear reviewThe team checks the product, guide, and history together.
