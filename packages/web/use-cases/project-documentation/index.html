Help people and AI understand your project

Code shows what a project does. It often does not explain why the team made each choice. A small knowledge base keeps those explanations close to the work.

Important project knowledge gets lost

Source code shows the result. It does not always explain why a pattern exists or what the team expects during review.

  • An AI agent guesses.It may choose a sensible pattern that conflicts with an earlier decision.
  • People repeat the same explanation.Important rules return to chats, calls, and review comments.
  • The guide becomes outdated.The next person sees new code but does not see the reason for it.

If the project does not save its explanations, every new person must discover them again.

First, set up Open Knowledge

Open Knowledge stores the project guide as linked Markdown files in Wiki/. Markdown is a simple text format that works with many tools.

  1. Open the project folder

    Use an existing project, or create this small demo project.

    $ mkdir example-project-docs
$ cd example-project-docs
$ git init

  2. Install Open Knowledge

    If okn version already works, skip this command.

    $ curl -fsSL https://openknowledge.sh/install | bash

  3. Create the knowledge base

    Start the guided setup and choose the AI tool used by the project.

    $ okn setup Wiki --interactive

Setup gives the AI agent a task. The task creates Wiki/, checks the files, and runs one useful search.

Start with three simple pages

Do not move every old note. Start with the information that the team often repeats during work and review.

Architecture
How the main parts connect and which limits a change must respect.
Team rules
Shared rules for code, tests, names, and review.
Decisions
Important choices, their reasons, and what future work must consider.
Wiki/
├── index.md
├── architecture/
│   └── system-overview.md
├── conventions/
│   └── code-and-review.md
└── decisions/
    └── 0001-context-next-to-code.md

These pages answer one useful question: what should someone know before changing this project?

See the same pattern in a Wikipedia example

The demo uses Wikipedia to show the same small structure. It is an example, not a replacement for Wikipedia policies. 

example-project-docs/
└── Wiki/
    ├── index.md
    ├── architecture/
    │   └── editorial-workflow.md
    ├── conventions/
    │   └── citations-and-sources.md
    ├── decisions/
    │   └── 0001-demo-scope.md
    └── sources/
        └── index.md

The architecture page explains how editors move content through the process. The team rules page explains source requirements. The decision page defines the demo scope.

The public demo must cite Wikipedia policies. It must also separate those policies from the demo explanation.

Give the AI agent context before it changes code

The AI agent usually needs only a few relevant pages. Open Knowledge search finds those pages and shows where each result came from.

Search runs on the local computer. It does not send the question to an AI model.

$ okn search Wiki "what context affects citation validation?"

The agent reads the relevant pages before it plans or changes code. It can name the pages that guide its work.

Add this simple rule to the project:

Before changing code:
1. Search Wiki for context relevant to the task.
2. Cite the Markdown files that guide the change.
3. Implement and test the code change.
4. If the change makes the context outdated,
   propose a Wiki update in the same change.

Review the code and its explanation together

After the code change, check whether the project guide is still correct. Ask whether the change affects architecture, team rules, or an earlier decision.

If it does, the agent proposes an update to the right Markdown page. A person reviews the code and explanation together. Not every code change needs a guide update.

These example files could appear in one review:

src/citations/validate.ts
tests/citations/validate.test.ts
Wiki/conventions/citations-and-sources.md
Wiki/decisions/0002-reject-bare-urls.md

Run validation before approval. It checks file structure, document details, Markdown, and links between local files. 

$ okn validate Wiki

The project keeps its knowledge

The goal is not perfect documentation. The goal is a clear project guide that changes with the work it explains.

  • Fewer repeated explanationsImportant rules live in reviewed pages instead of repeated messages.
  • Less lost contextDecision pages keep the reason after a chat or AI session ends.
  • One clear reviewReviewers can check the code and its explanation together.

Start with the question your team repeats

Create one architecture page, one team rules page, and one decision page. Ask the next AI agent to read them before a real code change.
