How to build project documentation that people and agents can use

Project documentation should explain how the work actually works—not merely describe the product. This guide uses a small Wikipedia knowledge base to show how one reviewed source can serve teammates, contributors, and AI agents.

First, set up Open Knowledge

Start inside the repository that will hold the Wikipedia demo. Open Knowledge will treat its Wiki/ directory as the reviewed source used throughout this guide.

  1. Create the repository

    Make an empty project and start its Git history.

    $ mkdir wikipedia-project-docs
$ cd wikipedia-project-docs
$ git init

  2. Install the CLI

    If okn --version already works, skip this command.

    $ curl -fsSL https://openknowledge.sh/install | bash

  3. Create the knowledge base

    Run the wizard and choose the agent you use for this project.

    $ okn setup Wiki --interactive

The setup wizard detects the project and prepares an agent task. That task creates or completes Wiki/, validates the bundle, and checks it with a representative search.

What project documentation needs to do

Useful documentation gives a reader enough context to make the next decision safely. It describes current behavior, the reasons behind important choices, the workflows people follow, and the boundaries they should not cross.

That reader may now be a person or an agent. The medium does not have to change. Both benefit from the same qualities: a clear structure, precise language, visible sources, and changes that pass through review with the rest of the project.

The goal is not to write more. It is to make the project’s working knowledge findable, reviewable, and specific enough to act on.

Use a repository, not another workspace

Put the canonical documentation beside the work it explains. Markdown gives people a readable source, Git gives the source a history, and review makes documentation changes visible before they become accepted project knowledge.

A concrete demo: documenting Wikipedia

Imagine a small knowledge base that explains Wikipedia’s editorial model. Its purpose is not to reproduce Wikipedia’s own documentation. It is an illustrative project that turns a complex, public workflow into a source-backed set of pages.

Start with the questions a new contributor—or an agent helping one—would need answered:

  • How does an article move from a draft to reviewed content?
  • Where are source and citation requirements documented?
  • How do editors discuss a disputed change?
  • Which pages define the current editorial workflow?

A small repository can give those questions a navigable shape:

wikipedia-project-docs/
├── README.md
└── Wiki/
    ├── index.md
    ├── concepts/
    │   ├── article-lifecycle.md
    │   ├── citations-and-sources.md
    │   └── talk-pages.md
    ├── workflows/
    │   ├── content-review.md
    │   └── dispute-resolution.md
    └── sources/
        └── index.md

This structure is illustrative. The published demo should cite the relevant public Wikipedia policies and clearly distinguish source material from the demo’s own explanation.

Make the structure readable before it is searchable

A reader should understand where a page belongs without needing search. Use an index to explain the map, group pages around the questions they answer, and link related concepts in the prose. Metadata should clarify the page—not compensate for unclear writing. 

---
type: Feature Documentation
title: Article lifecycle
tags: [wikipedia, editorial-workflow]
---

# Article lifecycle

An article can move through drafting, review, and
continued revision. See [Citations and sources]
(./citations-and-sources.md) for source requirements.

Open Knowledge reads the Markdown and frontmatter as an OKF bundle. The files remain useful in an editor, in a pull request, and anywhere else that can read plain text.

Browse the repository like documentation

A folder tree is good for authors. Readers often need a calmer view with rendered pages, working links, related documents, and enough source information to understand where a claim came from. 

$ okn view Wiki

Retrieve a focused answer, with its source

An agent rarely needs the entire repository. Search can return the relevant sections with their paths, headings, relationships, and source locations. The retrieval stays local and deterministic; it does not call an LLM. 

$ okn search Wiki "how are disputed article changes discussed?"

A useful result would point to concepts/talk-pages.md and workflows/dispute-resolution.md. The answer can then be checked against the exact pages that produced it.

Let an agent use the same repository

The last screenshot should connect the method to the use case: an agent answers a project question, but its response still points back to the reviewed Markdown. The repository remains the source; the agent is another reader of it.

Validate the source before it spreads

Documentation becomes more valuable when more systems depend on it—and more costly when its structure breaks. Validate the bundle before a change is merged or shared as agent context. 

$ okn validate Wiki

Validation checks frontmatter, document types, Markdown syntax, and local link targets. It cannot judge whether the explanation is true, but it can keep the source coherent enough to review.
